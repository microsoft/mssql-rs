# mssql-tds-cli

A command-line interface (CLI) tool for interacting with Microsoft SQL Server using the [mssql-tds](../mssql-tds) crate.

## Overview

`mssql-tds-cli` is a demonstration CLI built on top of the `mssql-tds` Rust crate, which provides a native implementation of the Tabular Data Stream (TDS) protocol. This tool allows you to connect to SQL Server instances, execute queries, and interact with databases directly from your terminal.

## Features

- Connect to Microsoft SQL Server using the TDS protocol
- Execute T-SQL queries and scripts
- View query results in the terminal
- Copy a query result between SQL Servers using batched TDS bulk load
- Demonstrates the capabilities and usage of the `mssql-tds` library

## Usage

```
cargo run --bin mssql-tds-cli -- --config-file-path <PATH_TO_CONFIG>
```

Or, if installed:

```
mssql-tds-cli --config-file-path <PATH_TO_CONFIG>
```

### Interactive mode

- `--config-file-path <PATH>`: Legacy option, accepted but not currently read.

**Note:**
Interactive mode still connects to `localhost:1433`, database `master`, as `sa`, reading the password from `/tmp/password`. The `copy` command below uses independently configurable connections.

### Server-to-server copy prototype

Create the destination table first, then supply the two SQL authentication passwords through environment variables (not command-line arguments):

```sh
# Set MSSQL_SOURCE_PASSWORD and MSSQL_DESTINATION_PASSWORD using your secret manager.
cargo run --release --bin mssql-tds-cli -- copy \
  --source-server tcp:source.example.com,1433 \
  --source-database SourceDb --source-user reader \
  --destination-server tcp:destination.example.com,1433 \
  --destination-database TargetDb --destination-user writer \
  --query 'SELECT id, payload FROM dbo.Source' \
  --destination-table dbo.Target \
  --batch-size 5000 --table-lock
```

Use `copy --help` for all options. `--source-password-env` and `--destination-password-env` select alternative environment variable names. TLS encryption and certificate verification are enabled; `--trust-server-certificate` bypasses verification on both connections for development only.

The command automatically streams `varbinary(max)`, `varchar(max)` and `nvarchar(max)` columns when all MAX columns in the result use these compatible encodings. It pulls one row at a time through `BulkCopy::write_to_server_stream`, relaying MAX payloads through a reusable **64 KiB buffer**. Destination writes provide backpressure: the next chunk is not read until the previous write finishes. NULL and empty values remain distinct, and text bytes retain their matching source/destination encoding and collation.

In streaming mode, `--batch-size` controls transaction boundaries, not buffering. A batch larger than the entire source does not require materializing the source or even a single MAX value. Memory for MAX payloads is independent of their size and row count, apart from protocol buffers; non-PLP values still use the existing value decoder.

Results without MAX columns, or with MAX types requiring different bulk encodings (such as XML, JSON or UDT), retain the existing two-batch typed-value pipeline. Those values may be materialized; use smaller batches for these fallback schemas.

This is **not raw TDS packet passthrough or end-to-end zero-copy**. MAX payload bytes are copied without text conversion but get new destination PLP (partially length-prefixed) framing; ordinary values are decoded and re-encoded. Source packet headers and ROW/NBCROW tokens cannot be forwarded unchanged. Neither path uses CSV, hex, base64, intermediate files or per-row INSERTs.

Prototype constraints:

- Supply one SELECT result with the same column names, order, types, lengths, precision, scale and collations as the destination. Use aliases/CASTs in the SELECT where necessary. No schema creation, conversions, computed/rowversion destination columns, or Always Encrypted migration is supported.
- Identity columns are generated by the destination by default: omit them from the SELECT. Use `--keep-identity` and include those columns to preserve their values.
- Rows are appended, never truncated. NULLs are preserved and constraints checked; triggers are not fired. `--table-lock` requests a bulk update lock and can block other users.
- Each batch commits separately. On failure, earlier batches remain committed; blindly retrying can duplicate data. Additional result sets are rejected, but only after the first has been copied.
- `--timeout` controls bulk copy (default 30 seconds; 0 disables it). Streaming uses one bulk operation across all batches, so its timeout covers the whole copy after the source query has started, including waiting for the next row. Individual source column/chunk reads are also bounded. The fallback pipeline retains a separate bulk timeout for each buffered batch. Neither mode applies this timeout to initial source-query execution.
- The final summary reports elapsed transfer time and rows/second, excluding connection setup. Use a release build and compare batch sizes on representative servers; no throughput claim has been benchmarked yet.

The opt-in integration tests check streamed binary and text payloads across chunk and batch boundaries, NULL/empty values, trailing columns, empty results, schema errors and failed transfers. They use two connections to one test SQL Server and temporary tables:

```sh
# Export DB_HOST, DB_PORT, DB_USERNAME and SQL_PASSWORD from your test environment.
cargo nextest run -p mssql-tds-cli --run-ignored ignored-only
```

```
cargo run --bin mssql-tds-cli -- --config-file-path ./config.toml
```

## Why use this CLI?

- To test and debug the `mssql-tds` protocol implementation
- As a reference for building your own TDS-based tools in Rust
- For quick, scriptable access to SQL Server from the command line (with future enhancements)
